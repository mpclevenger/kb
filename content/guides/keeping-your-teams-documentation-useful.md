Out-of-date documentation is a risk in its own right: people follow steps that no longer work, controls drift away from what is written, and reviewers find gaps the team didn't know about. A small amount of structure keeps a team's wiki trustworthy without much effort.

## Give every page an owner

- Each page names an owning role, not whoever happened to write it first.
- Each page shows when it was last reviewed and when it is next due.
- When an owner moves on, their pages move to someone else as part of the handover.

## Use a simple, predictable structure

- Organize by system or service, then by type: overview, procedures, runbooks, decisions.
- Use the same headings for the same kind of page, so readers know where to look.
- Start each page with one or two sentences on what it covers and who it is for.
- Link rather than copy. One page holds each fact, and others point to it.

## Write for the reader

- Lead with what the reader needs to know or do.
- Keep pages short. Split a long page by task rather than adding to it.
- Use plain words, and define system names and abbreviations once.
- Show examples of good evidence or correct output where it removes doubt.

## Review on a rhythm

- Review pages that support controls at least once a year, and whenever the system or control changes.
- Review runbooks after each real use.
- Archive or delete pages that are no longer true. A clearly retired page is better than a misleading one.
- Track open documentation gaps like any other work item, with an owner and a date.

## Connect documentation to risks and controls

- Link each control procedure to the control it supports, and say which risk it addresses.
- Link runbooks from the procedures and system pages that depend on them.
- Keep the minimum set of system documentation current. See [What every system should have documented](/guides/what-every-system-should-have-documented/).

If you're unsure, Tech Risk can help.
